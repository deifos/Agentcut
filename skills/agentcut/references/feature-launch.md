# Feature Launch

Use this guide for the Feature Launch chat action or a request to announce one new feature or capability. Also read `product-launch.md` for brand, capture, visual, sound and final review standards. Feature Launch has its own brief and story; it is not a whole-product introduction or a step-by-step lesson.

## Identify the feature before work

For a bare request, ask which feature is new and what people can now do. A product URL or an old launch alone does not identify the feature. Ask locally before an agent run when possible. Do not scan other projects or shared libraries to guess. Preserve deliberate attachments, current brief, selected style and music. With supplied context, inspect it first and ask only for missing facts that affect the video.

Use the assigned canvas video. A populated source gets a separate target, timeline and chat; keep the source unchanged. Reuse a truly empty video. Explicit edits keep their target. This is the standard creative workflow, not the limited release-job API.

## Plan the story

Write the audience, one new benefit, one verified claim and a shot list in notes.md. Default flow:

1. **New benefit.** Open with what people can now do. Name the feature when it helps recognition.
2. **Feature in action.** Show a real action and its visible result, with enough context to understand what changed.
3. **Outcome.** Make the benefit visible. Use a supported before/after only when the evidence exists. Do not invent time savings, performance figures or customer claims.
4. **Next step.** End with one useful action: try the feature, open its location, or read the announcement. State verified availability or plan restrictions when relevant.

The problem statement is optional. Existing users often know the problem; do not delay the feature with a repeated product introduction. For a new audience, add only the context required to understand the benefit. Keep one main feature; do not turn the video into a feature list. Choose duration from the material and channel rather than a fixed formula. Respect requested length, aspect ratios, voice, captions and music.

For example, a canvas-versions announcement could show making two independent versions, then switching between their timelines and chats. The visible result supports “explore another version while keeping the original.” A How-to would instead explain each step needed to complete that task.

## Build and verify

Follow the full Agentcut skill: inspect real assets and the component/3D libraries, plan intentional motion and camera changes, use editable tracks, coordinate music and sound effects, and retain final full-picture and audio review. Do not replace the process with a fixed animation recipe. Use the user's own footage or safe real-app capture. If proof or access is missing, ask for it before building a false demonstration.

Use `sound.md` for voice and music. Generic voice-over uses local Kokoro; a paid voice requires explicit user selection. A silent announcement is valid when requested. If voice is used, inspect the take, check its words and use transcription timings for accurate captions. Music must support the action and leave the message clear.

Before delivery, verify that viewers can identify the feature, understand its new benefit, see evidence in the actual demonstration, and know the next step. Check small-screen readability, output formats, timing, asset paths, picture and sound. Deliver the editable result only after the normal final review passes.
